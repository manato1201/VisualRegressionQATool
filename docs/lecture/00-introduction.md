# 第 0 回 ビジュアル回帰とは(まず、全体の見取り図)

> 所要時間の目安: 1 時間 / 前提: Python の基本

## この回のゴール

- **ビジュアル回帰テスト**が何を解決するかを説明できる。
- このツールの設計の軸「**撮影を決定的にしてから、評価はシンプルなピクセル比較に留める**」の理由を説明できる。
- パイプライン(撮影指示 → 撮影画像 → 基準画像 → 差分画像 → 評価結果)の各段の役割が分かる。
- 画像を 2 枚比べて、合格 / 不合格を出す最小の例を動かせる。

## 1. 解きたい問題

見た目(画面・ゲームのシーン・UI)は、コードを直すたびに**意図せず変わる**ことがあります。ボタンが 1px ずれる・テクスチャが抜ける・色が変わる。人が毎回目で確かめるのは、大変で、見落とします。

**ビジュアル回帰テスト**は、「**正しいと認めた画像(基準画像)**」と「**いまの撮影画像**」を機械で比べ、**違いがあれば知らせる**仕組みです。

## 2. 設計の軸: 先に「撮影」を決定的にする

画像の比べ方には、「賢い」方法(SSIM などの知覚的な類似度)もあります。でも、このツールは**あえて使いません**。

| 方針 | 理由 |
|---|---|
| **撮影を決定的にする**(時計・乱数・動きを固定) | 同じ入力なら、**毎回まったく同じ画像**になる。違いが出たら、それは**本物の変化** |
| **評価は、ピクセルごとの比較に留める** | 「類似度 0.97」は、**何が違うのか**を説明できない。ピクセルの差は、**「どこが・何ピクセル違うか」**を、そのまま説明できる |

つまり、「**差分が何を意味するのかを、明確にする**」ことを、最優先にしています。賢い評価で誤魔化さず、**揺れの原因(撮影)を先に潰す**。

## 3. パイプライン

```text
撮影指示 → 撮影画像 → 基準画像 → 差分画像 → 評価結果 → DB
(Capture   (Captured   (Reference  (Diff       (Evaluation
Instruction) Image)     Image)      Image)      Result)
```

| 段 | 意味 | 例 |
|---|---|---|
| **CaptureInstruction** | どう撮るか(シーン・カメラ・乱数のシード・固定する時刻) | `scene=title`・`seed=1`・`fixed_time=0.0` |
| **CapturedImage** | 実際に撮れた画像(ビルドの版つき) | `build_version=v12` |
| **ReferenceImage** | **人が「これが正しい」と承認した**撮影画像 | 承認されたものだけが基準になる |
| **DiffImage** | 撮影画像と基準画像の差を、画像にしたもの | 違うピクセルを**マゼンタ**で塗る |
| **EvaluationResult** | 合格(pass)・不合格(fail)・不安定(flaky) | |

## 4. 最小の例: 2 枚を比べる

```python
# 実行できる
import io

import numpy as np
from PIL import Image

from app.diff_engine import PixelDiffEngine


def png(array) -> bytes:
    buffer = io.BytesIO()
    Image.fromarray(array).save(buffer, format="PNG")
    return buffer.getvalue()


reference = np.full((8, 8, 3), 100, dtype=np.uint8)   # 8x8 の灰色
same = reference.copy()
changed = reference.copy()
changed[2, 3] = (255, 0, 0)                             # 1 ピクセルだけ赤に

engine = PixelDiffEngine()
for label, captured in [("同じ画像", same), ("1 ピクセル違う", changed)]:
    result = engine.compare_bytes(png(captured), png(reference))
    print(f"{label:8} 判定={result.verdict}  差分={result.diff_pixel_count}px ({result.diff_percentage:.2f}%)")
```

```text
# 出力
同じ画像     判定=pass  差分=0px (0.00%)
1 ピクセル違う 判定=fail  差分=1px (1.56%)
```

- 既定では、**1 ピクセルでも違えば fail**(厳密)。64 ピクセル中の 1 つ = 1.56%。
- 現実の画像には、JPEG のようなノイズや、わずかなサイズ違いがあります。それを**賢い評価に頼らずに**扱うための 3 つのつまみと、サイズ違いの扱いを、次の回で学びます。

## 確認問題

1. このツールが、SSIM などの類似度でなく、ピクセルごとの比較を選んだのは、なぜですか。
2. 「撮影を決定的にする」とは、何を固定することですか。
3. 基準画像(ReferenceImage)は、なぜ「承認されたものだけ」なのですか。
4. この回の例で、1 ピクセルの違いが 1.56% になるのは、なぜですか。

## 解答

1. 類似度の数字は、**何が違うのかを説明できない**。ピクセルの差は、「どこが・何ピクセル」を直接示せる。賢さより、**差分の意味の明確さ**を優先している。
2. 時計(アニメーションの時刻)・乱数のシード・カメラ・動き(`reduce_motion`)など、**画像が揺れる原因**。同じ指示なら毎回同じ画像になるようにする。
3. 承認されていない画像を基準にすると、**誤った見た目を「正しい」と比べて**しまう。昇格(承認)の段を置いて、人の判断を 1 回挟む。
4. 8 × 8 = 64 ピクセルのうち 1 つ。1 ÷ 64 × 100 ≈ 1.56%。

## まとめ

- ビジュアル回帰 = **基準画像と撮影画像を機械で比べ、違いを知らせる**。
- 軸は「**撮影を決定的に → 評価はシンプルなピクセル比較**」。差分の意味を、明確に保つ。
- パイプラインは 撮影指示 → 撮影画像 → 基準画像 → 差分画像 → 評価結果。
- 次の回は、比較の中身(`PixelDiffEngine`)。
